# SRS Revision Annotation Rules

## Annotation Goal

Human annotators do not directly rewrite the SRS and do not re-review the
entire SRS from scratch. Instead, they review each model-generated
`Candidate Issue` and decide whether the issue is correct, whether it is
supported by evidence, and whether the SRS should be revised.

The annotation unit is each `Rxxx` issue in `human_srs_review.md`.

## Annotation Inputs

Each annotator should inspect the following materials together:

- `final_srs.md`: the SRS under review.
- `evidence_pack.json`: evidence snippets such as `E001`, `E002`, and so on.
- `human_srs_review.md`: candidate issues generated by the model.
- `Model proposed SRS change` / `proposed_srs_change`: the candidate SRS
  revision proposed by the model for each issue.
- `Optional human revised fix`: the annotator's own revision suggestion when
  the model-proposed fix is unsuitable.
- External files, API specifications, or architecture diagrams referenced by
  the model suggestion when additional checking is necessary.

## Main Label: Human Decision

Each `Rxxx` issue must receive exactly one main label. This label is used for
inter-annotator agreement analysis.

| Label | Meaning | Use when |
| --- | --- | --- |
| `ACCEPT` | Accept the issue | The issue identified by the model is real, evidence-supported, and requires an SRS change. |
| `REJECT` | Reject the issue | The issue does not exist, lacks evidence support, is over-inferred by the model, or is already covered by the SRS. |
| `NEEDS_DISCUSSION` | Needs discussion | Existing evidence is insufficient, evidence snippets are truncated, or the annotator needs the complete file, architecture diagram, or domain knowledge. |
| `PARTIAL_ACCEPT` | Partially accept the issue | The model issue mixes multiple claims, some of which are valid and some of which are invalid. |

## Acceptance Rules

Mark an issue as `ACCEPT` only when all of the following conditions are met:

1. The issue identified by the model can be located in `final_srs.md`.
2. The issue affects the completeness, accuracy, verifiability, traceability,
   or scope definition of the SRS.
3. The evidence in `evidence_pack.json` directly or strongly supports the
   judgment.
4. The issue is actionable and can be converted into a concrete revision
   suggestion.
5. The issue is not a duplicate of another accepted issue.

For example, if the evidence explicitly shows a POST endpoint but the SRS
omits the corresponding functional requirement, the issue can be marked as
`ACCEPT`.

## Rejection Rules

Mark an issue as `REJECT` in the following cases:

1. The model is only making a common-sense inference without evidence support.
2. The model claims that the SRS is missing content that is already covered by
   the SRS.
3. The content requested by the model is outside the current SRS scope.
4. The model misinterprets the evidence.
5. The issue is only a style preference and does not affect requirement
   quality.
6. The issue completely duplicates another issue.

Be careful with claims such as:

```text
"standard REST resource design strongly imply..."
```

If the evidence does not directly support such a claim, do not mark it as
`ACCEPT`. `NEEDS_DISCUSSION` is usually more appropriate.

## Discussion Rules

Mark an issue as `NEEDS_DISCUSSION` in the following cases:

1. The annotator is uncertain about the model's statement.
2. The three annotators have clear disagreement about severity or about whether
   the issue is a real defect.

## Partial Acceptance Rules

If one issue mixes multiple problems, mark it as `PARTIAL_ACCEPT`.

For example, suppose the model says:

```text
The SRS lacks A/B routing, shadow traffic, enricher, UI, and version lifecycle.
```

If A/B routing and version lifecycle are supported by evidence but UI is not,
do not simply mark the issue as `ACCEPT`. Mark it as `PARTIAL_ACCEPT` and
explain in the note which claims are accepted and which are rejected.

## Reviewing Model-Proposed SRS Changes

For each `Candidate Issue`, the model also provides a
`Model proposed SRS change`, which describes how the model suggests revising
the SRS. Human annotators must read this proposed change while reviewing the
issue.

Annotators should decide whether the proposed change resolves the issue. In
particular, check the following points:

1. Whether the proposed change is supported by evidence. It must not introduce
   functions, technologies, or architectural assumptions absent from the
   evidence.
2. Whether it changes only the minimum scope related to the issue instead of
   rewriting the entire SRS.
3. Whether it points clearly to the relevant SRS section, requirement ID, or
   table location.
4. If it adds a new requirement, whether it includes necessary fields such as
   description, trigger/input, system behavior, output, priority,
   verification, and source evidence.
5. If it revises an NFR or constraint, whether the revised statement is as
   verifiable as possible and preserves the evidence ID.
6. Whether it preserves traceability by avoiding unsupported new content and by
   not deleting evidence that remains valid.
7. Whether it avoids contradictions with existing FRs, NFRs, data
   requirements, constraints, or the traceability matrix.

If the model-proposed change is correct, the annotator can simply state that
the model suggestion can be adopted.

If the model-proposed change is unsuitable, do not reject the issue only
because the proposed fix is poor. The main label should still be decided based
on whether the issue itself is valid. Then write the correct fix in
`Optional human revised fix`.

Common handling patterns:

- If the issue is valid but the model fix is incomplete, mark `ACCEPT` and add
  missing fields or more precise SRS text in `Optional human revised fix`.
- If the issue is valid but the model fix introduces an unsupported claim, mark
  `ACCEPT` and explain that the model suggestion should not be adopted and
  should instead be revised.
- If the issue is partially valid, mark `PARTIAL_ACCEPT`, explain which claims
  are valid in the note, and revise only the valid part in
  `Optional human revised fix`.
- If the issue is invalid, mark `REJECT`, do not adopt the model-proposed
  change, and explain the rejection reason in the note.
- If evidence is insufficient, mark `NEEDS_DISCUSSION` and specify the complete
  file, API specification, architecture diagram, or domain knowledge that must
  be checked.

Example:

```text
Human decision: ACCEPT
Optional human note:
> The issue is valid, but the model suggestion also adds UI content to the SRS,
> which is not supported by the current evidence.

Optional human revised fix:
> Add only the FR related to router version lifecycle and cite E003. Do not add
> a UI requirement.
```

## Category Rules

Model-review issue categories:

- `missing_requirement`: evidence exists, but the SRS omits it.
- `unsupported_claim`: the SRS contains a claim that is not supported by
  evidence.
- `contradiction`: the SRS conflicts with the evidence.
- `ambiguity`: the statement is ambiguous and cannot be verified consistently.
- `non_verifiable`: the requirement lacks observable acceptance criteria.
- `traceability`: evidence references are missing, incorrect, or confusing.
- `scope`: the system scope is too broad, too narrow, or poorly bounded.
- `architecture_detail`: architecture diagrams, components, connections, or
  deployment information are missing or questionable.
- `other`: the issue cannot be assigned to any category above.

## Annotation Process

1. Three annotators jointly read 2-3 examples to align on the rules.
2. Randomly sample about 10% of issues for pilot annotation.
3. Discuss disagreements and revise the rules.
4. After freezing the rules, the three annotators independently review all
   samples or the overlapping subset.
5. For each issue, annotate `decision`, revise `severity` and `category` when
   necessary, and review the model's `Model proposed SRS change`.
6. If the model-proposed change is inconsistent with the evidence, scope, or
   SRS format, write a human revision suggestion in
   `Optional human revised fix`.
7. Before discussion, compute agreement metrics such as Fleiss' Kappa or
   Krippendorff's Alpha.
8. Resolve disagreement issues by majority vote. If there is no majority,
   resolve them through adjudication.
9. Use the adjudicated result as the final human judgment.
